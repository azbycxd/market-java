## 6. Auth 边界

两个 Controller 都在调用领域 Service 前从 `AuthenticatedUserProvider.getAuthenticatedUserId()` 获取可信身份：

- Order Facts 请求 DTO 仅含 `outTradeNo`，没有身份字段；
- Joinable Team Facts 请求 DTO 仅含 `activityId`，并通过 `@JsonAnySetter` 拒绝额外字段；
- `DevHeaderAuthenticatedUserProvider` 仅在 active profile 是 `dev` 或 `test` 且 `agent.facts.dev-header-auth.enabled=true` 时读取开发 Header；生产环境不满足这两个条件时返回空身份。

因此 body 中的 `userId` 不能成为任何一个 API 的可信业务身份来源，未为联调降低认证要求。

## 7. 只读边界

在两次 Facts API 调用前后，对关键表执行了仅 `COUNT(*)` 的只读核验：

| 表 | 调用前 | 调用后 |
| --- | ---: | ---: |
| `group_buy_order_list` | 5 | 5 |
| `group_buy_order` | 3 | 3 |
| `notify_task` | 3 | 3 |

本次两条 Facts API 调用未造成可观察到的新增业务记录或通知任务记录，也未执行写型 HTTP 调用。

## 8. Java 背景任务风险

当前应用仍包含既有调度任务：`TimeoutRefundJob` 每分钟运行一次，`GroupBuyNotifyJob` 每日运行一次。它们不由本次 Facts 请求触发，但共享 dev 环境可能在其他时间造成背景状态变化。

本次前后快照未见三张关键表变化；后续 Python 多工具联调应继续把 Agent Facts 调用和此类既有后台任务区分记录，且不要通过修改业务数据来制造候选队伍。
