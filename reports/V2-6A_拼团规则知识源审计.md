# V2-6A 拼团规则知识源审计

## 1. 审计范围

本次为只读源码与文档审计；未访问 Python Agent、未修改 Java 业务代码、未访问数据库、未创建向量库或 embedding。

审计范围包括根 `README.md`、`docs/` 下的 Markdown/SQL 备份、API DTO/Controller、活动与交易领域 Service、Rule Filter、Strategy、Enum、VO、Repository/Mapper 的查询与状态更新路径、以及超时与通知 Job。

## 2. 当前项目已有业务文档情况

现有根 README 和 tag 文档主要是检出、构建、镜像和部署说明，不构成面向用户的拼团规则文档。`docs/agent` 的内容是 Agent API 合同及验收记录，适合追溯接口边界，不应直接作为客服知识文章。

项目确有较丰富的业务规则证据，但主要存在于 Java 代码：Enum、领域实体、锁单/结算/退单规则链、人群标签节点、优惠计算策略和 Job。故首批规则知识应由这些证据人工整理成简洁中文条目，并带上版本与来源；不能把源码、SQL、Mapper 或配置全文切块入库。

## 3. 三类信息分类

| 分类 | 发现的内容 | 处理结论 |
| --- | --- | --- |
| A. 实时业务事实 | 订单当前状态、团队人数/有效期、活动状态、当前可加入候选团队、活动团队统计 | 继续由 `get_order_facts` 和 `get_joinable_team_facts` 提供；不进入 RAG 主知识库。 |
| B. 确定性业务执行规则 | 锁单前活动/时间/次数/库存校验，支付结算，超时退单，团队状态迁移，标签与优惠计算 | Java 仍是唯一最终判定与执行者。可将稳定且用户可解释的部分整理为规则说明，但 RAG 不得据此作某个用户是否可参与、应否退款、是否支付成功的最终判断。 |
| C. 稳定解释型知识 | 拼团流程、人数指标与状态语义、活动有效期含义、参与限制、标签影响、优惠类型、退单状态语义、Agent 能力边界 | 可作为经过筛选的知识条目候选。 |

## 5. 不适合进入 RAG 的内容

- 任一用户的订单、团队、活动、资格、人数、有效期、候选队伍或统计数值；这些均为实时 Facts。
- 是否允许当前用户锁单、是否仍可参与、活动现在是否有效、折后应付金额、是否应退单等实例判断；这些取决于当前时间、数据库、渠道、标签、库存和状态，必须由 Java Rule/Service 决定。
- 全量源码、SQL、Mapper、Redis 键、连接配置、Job 锁名、通知任务参数、测试样例、用户标识、订单号、回调细节和任何基础设施实现。
- 代码中的临时注释或与实际 cron 不一致的说明；不能未经核验变成正式规则知识。

## 6. RAG 与 Java Facts 的职责边界

RAG 可解释“`completeCount` 的一般含义”“团队通常何时完成”“活动有效性通常受哪些规则影响”。

RAG 不可回答“你的订单现在完成了几人”“你现在还能否参加”“本活动当前是否有效”“现在有哪些团可加入”。这些问题必须分别调用 Order Facts 或 Joinable Team Facts，必要时由 Java 业务规则继续校验。

## 7. RAG 与 Java Rule 的职责边界

RAG 是解释层，不是裁决层。它可把活动有效期、次数限制、标签、容量和优惠机制解释为一般规则；但不能自行计算价格、判断标签资格、判断库存、选择退单策略或触发任何状态变化。Java Rule Filter、Strategy、Repository 和事务路径保留为唯一执行权威。

## 8. 退款语义边界

源码存在本地“退单”领域和三类状态组合策略，也会写入本地通知任务并发送退单消息。但本项目没有独立退款账本、退款状态、退款金额、退款完成时间或支付渠道退款完成查询。

因此知识条目只能准确表述：`CLOSE` 表示本项目交易订单进入“用户退单”关闭状态，并在重复退单检查中视为已处理的本地退单状态。**它不能表述为资金已经退款到账。** 对“已支付”路径，源码可证明本地逆向处理及消息通知存在，不能证明外部资金退款完成。

## 10. 推荐首批知识范围

唯一建议的初始知识域为：**拼团规则、状态解释与退单语义边界**。

建议首批 **14** 条，覆盖上表中流程、开团/参团、成团、人数指标、团队/订单/活动状态、有效期、次数限制、标签影响、优惠类型、可加入团队的一般原则、超时处理、未成团退单和 `CLOSE` 边界。每条均应附来源等级；优先 LEVEL_2，流程类 LEVEL_3 要明确“根据实现归纳”。

不把实时候选队伍、活动统计、具体订单状态或精确价格作为条目内容。

## 11. 是否值得使用 RAG

`RAG_JUSTIFIED = YES`。理由不是技术流行，而是源码可支持至少 14 条相对稳定、可解释、用户可能询问且无需每次读取某一用户实时数据的规则知识；同时存在清晰的 Facts 与确定性执行边界。

前提是采用受治理的精选条目集，而不是对整个仓库向量化。由于项目缺少正式用户业务文档，首批条目必须在入库前做业务审阅和版本管理；若无法建立该审核流程，应降级为同一批经过审阅的静态 Rule Catalog，而非导入未筛选源码。

## 12. 安全与隐私约束

知识库不得含用户 ID、订单号、手机号、地址、Header、Token、密码、API Key、数据库连接信息、Redis 键、测试账号、`notify_task.parameter_json`、真实订单数据、SQL、Mapper 或基础设施配置。知识检索结果只能提供规则解释，不可泄露内部实现或替代认证后的实时 Facts。

## 13. Remaining Risks

- 正式用户业务文档不足，首批内容大多为 LEVEL_2 代码证据，需建立源码变更后的知识版本复核机制。
- `TimeoutRefundJob` 的注释与实际 cron 不一致；任何时间频率类文档必须以执行代码复核。
- 人群标签、渠道黑名单、库存和活动时效均强依赖实时状态；检索文本必须显著提示“以实时 Java 校验为准”。
- 本地退单状态不证明支付渠道资金到账；该限制需同时出现在退款相关知识条目和回答策略中。
