# V2-6B 拼团规则知识目录编制

## 1. Catalog 设计

已新增可版本化的正式规则知识目录：

- `docs/agent/knowledge/group_buy_rules_v1.json`
- `docs/agent/knowledge/README.md`
- `docs/agent/knowledge/validate_catalog.py`

目录顶层包含 `catalog`、`version`、`generated_from`、`review_date`、`entry_count` 和 `entries`。每个条目均含稳定英文 snake_case `knowledge_id`、中文标题/正文、分类、来源类型、来源等级、可追溯源码文件/符号、版本、少量标签及 `requires_realtime_facts`。

这是业务知识数据与治理材料，不是 Java Runtime 配置；未修改 Controller、Rule、Strategy、Job、Mapper、SQL、数据库或服务配置。

## 2. 最终条目数量

实际条目数为 **16**，处于计划的 12～18 条合理粒度内。人数指标合并为一个条目，退款语义按未成团、已成团影响和 `CLOSE` 边界分别保留，避免重复又保证安全边界独立可检索。

## 4. 实时 Facts 边界

所有会受订单、团队、活动、时间、用户、标签、库存或支付状态影响的条目均标记 `requires_realtime_facts=true`。正文只解释一般含义，并明确具体用户实例须查询实时 Facts 或由 Java 校验。

因此目录不会回答具体订单当前状态、当前团队人数、活动目前是否有效、可加入团队有哪些、用户是否有资格参加或当前应付价格。前两类问题继续由已实现的两个 Java Facts API 提供。

## 5. Java Rule 裁决边界

目录可解释活动有效期、参与次数、人群标签、优惠方式、容量和退单状态；它不能裁决用户资格、库存、价格、锁单、活动可用性或退款策略。Java Service、Rule Filter、Strategy 和事务路径仍是唯一的判定与执行权威。

## 6. CLOSE / 退款语义

`group_buy_close_status_semantics` 是独立的重点安全条目，且来源于 `TradeOrderStatusEnumVO.CLOSE`、重复退单检查与退单通知策略。

它明确规定：`CLOSE` 是当前项目交易订单进入用户退单关闭状态。源码可证明本地退单处理、本地逆向状态更新和通知消息路径；不能证明支付渠道完成资金退款，也不能提供退款金额、退款完成时间或到账时间。

## 7. LEVEL_3 条目

仅 `group_buy_basic_flow` 使用 LEVEL_3。它跨锁单、支付结算和超时处理路径归纳流程，正文使用“当前项目实现体现”的非承诺性表述，不将流程归纳伪装成正式产品承诺。

## 8. 安全过滤

Catalog 正文没有用户标识、订单号、手机号、地址、Header、Token、密码、API Key、连接信息、Redis 键、通知参数、真实订单数据、SQL、Mapper 或基础设施配置。

静态校验会对整个 JSON 拒绝明显敏感/传输模式、疑似长订单号、绝对源码路径，以及缺失或无效的来源字段。目录仅保留仓库相对路径供治理使用。

## 9. 静态质量检查

执行命令：

```powershell
python docs/agent/knowledge/validate_catalog.py
```

实际结果：

```text
CATALOG_STATIC_VALIDATION=PASS entries=16
```

脚本只依赖 Python 标准库，检查：JSON 可解析、顶层字段、声明条目数、唯一且合法的 knowledge ID、必填字段、合法来源等级、非空来源文件/符号/标签、来源文件在当前仓库存在、布尔事实标记、非绝对路径、敏感模式与疑似测试订单号。

未修改 Java Runtime。没有业务逻辑、接口、数据库、SQL、Job、Redis、RabbitMQ 或配置变更。

## 12. 后续 Python Agent 如何消费

后续 Python Agent 阶段可先执行或集成同等静态校验，再只读加载 versioned Catalog，根据 `title`、`content`、`tags` 和 `category` 做检索。检索命中的规则说明必须与实时 Facts 和 Java Rule 边界共同使用；本阶段没有实现检索、向量库、Tool、Prompt 或 Python 代码。

## 13. Remaining Risks

- 正式用户业务文档不足，目录主要依赖 LEVEL_2 源码证据；业务规则改动时需要人工复核并升级版本。
- `TimeoutRefundJob` 的注释与可执行 cron 不一致；正文已避免承诺处理频率。
- 人群、库存、价格、活动时间和退款策略存在实时依赖，调用方必须遵守 `requires_realtime_facts` 与 Java 裁决边界。
- `CLOSE` 不能被回答层扩展解释为资金退款到账。
